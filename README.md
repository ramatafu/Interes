# Interes (программа в стадии разработки)

Оффлайн-приложение для Android и Windows в духе Pinterest: тематические доски
с фотографиями, полноэкранный просмотр, drag-n-drop внутри доски, прозрачное
окно с фото.

## Технологии
- **Kotlin Multiplatform** — общий код для Android и Windows.
- **Compose Multiplatform** — UI (Jetpack Compose на Android, Compose Desktop
  на Windows) на одном и том же API, минимум дублирования.
- **SQLDelight** — локальная база (доски, фото, порядок в доске), одна схема
  на обе платформы, разные драйверы.
- **Никакого сетевого кода.** На Android разрешение `INTERNET` не объявлено —
  это не только архитектурное решение, но и системный запрет со стороны ОС.

## Статус этапов

- [x] **Структура проекта** — модули, БД, репозиторий, точки входа на обеих
      платформах компилируются и общаются с shared-модулем.
- [x] **Доска с фото** — `PhotoBoardGrid` (masonry, `LazyVerticalStaggeredGrid`)
      с drag-n-drop через отслеживание реальных bounds карточек, импорт фото
      через `rememberImagePicker` (SAF на Android / `FileDialog` на Desktop).
      Код общий для обеих платформ (`shared/src/commonMain/.../ui`).
- [x] **Полноэкранный просмотр** — `PhotoViewerScreen`: `HorizontalPager` для
      свайпа между фото (на любое число фото в доске, без ограничений) +
      pinch-to-zoom/пан, двойной тап для быстрого зума.
      **Важный исправленный баг:** обычный `detectTransformGestures`
      потребляет вообще любое перемещение пальца как pan — включая простой
      одиночный свайп влево/вправо без всякого масштабирования. Событие
      "съедалось" внутри `ZoomableImage` и никогда не доходило до
      `HorizontalPager` снаружи — из-за этого пролистывание между фото не
      работало вообще, независимо от их количества в доске. Заменено на
      свой `detectZoomAndPanWhenActive`: он потребляет жест только когда
      это реально масштабирование (2+ пальца) или фото уже увеличено
      (`scale > 1`) — в остальных случаях одиночный свайп проходит
      непотреблённым и достаётся `HorizontalPager`. Заодно двойной тап и
      zoom/pan объединены в один `pointerInput` с двумя сопрограммами (та
      же логика, что и в `PhotoBoardGrid`, — два отдельных `pointerInput`
      на одном узле конкурируют за один поток касаний).
- [x] **Прозрачность — до уровня рабочего стола ОС** — ползунок 0–100% в
      `PhotoViewerControls` управляет прозрачностью **всего приложения
      целиком** (`AppRoot.kt`), а не только просмотрщика или конкретного
      фото. Кнопка закрытия, счётчик страниц и сам ползунок вынесены в
      отдельный composable и рисуются СНАРУЖИ затухающего слоя — остаются
      полностью видимыми при любом значении, иначе при 0% нечем было бы
      вернуть прозрачность обратно. Сбрасывается на 100% при закрытии
      просмотрщика и при пролистывании на другое фото.

      **История в три шага** (каждый — реакция на уточнение от заказчика):
      1. Первая версия делала прозрачным только само изображение поверх
         сплошного чёрного фона — математически это неотличимо от
         затемнения (`пиксель × alpha` на чёрном = уменьшение яркости), а
         не прозрачность.
      2. Исправлено на прозрачность слоя "чёрная подложка + фото" вместе —
         сквозь экран стала проступать доска позади (`BoardScreen` остаётся
         в композиции, пока открыт просмотрщик). Это уже настоящая
         прозрачность, но только **внутри приложения**.
      3. По факту нужно было **до уровня рабочего стола ОС**. Для этого
         недостаточно только Compose-кода — Compose может рисовать сколько
         угодно прозрачных пикселей, но если формат самого окна непрозрачный
         (обычное поведение по умолчанию), система физически не смешивает
         их с тем, что находится позади окна. Понадобились изменения на
         уровне платформы:
         - **Android:** тема `Theme.Interes`
           (`androidApp/src/main/res/values/themes.xml`) объявлена
           `windowIsTranslucent = true` с прозрачным `windowBackground`.
           Дополнительно ничего в Kotlin-коде включать не нужно — этого
           достаточно, чтобы система реально смешивала полупрозрачные
           пиксели Compose с рабочим столом/лаунчером позади. На остальных
           экранах эффект незаметен, так как там Compose сам рисует
           полностью непрозрачный фон.
         - **Windows:** у Compose Desktop окно не может на лету
           переключаться между обычным и прозрачным — это фиксируется один
           раз при создании. Поэтому главное окно (`desktopApp/.../Main.kt`)
           теперь **всегда** `undecorated = true, transparent = true`. Плата
           за это — пропала системная рамка (заголовок, кнопки свернуть/
           закрыть), поэтому добавлена своя тонкая панель сверху
           (`AppTitleBar`) с перетаскиванием окна (`WindowDraggableArea`) и
           собственными кнопками свернуть/закрыть — она тоже всегда
           непрозрачна.
         - Сам общий затухающий `graphicsLayer { alpha = ... }` живёт в
           `AppRoot.kt` (общий код) и оборачивает буквально всё содержимое
           приложения — список досок, доску, сам просмотрщик — одним слоем.

      **Что стоит перепроверить на реальных устройствах:** поведение
      `windowIsTranslucent` может немного отличаться между версиями
      Android/производителями (в частности — что именно видно позади:
      лаунчер, обои или чёрный экран, если в стеке задач за приложением
      ничего нет). На Windows альфа-канал undecorated-окна тоже зависит от
      связки JDK/GPU-драйвера — см. предупреждение в коде
      `desktopApp/.../Main.kt`.
- [x] **Список досок и управление ими** — `BoardsListScreen`: стартовый
      экран с карточками досок (превью — первое фото доски), кнопка "+"
      создаёт доску и сразу открывает её. Долгое нажатие на карточку — меню
      "Переименовать / Удалить". Удаление доски каскадно удаляет её фото и
      в БД (PRAGMA foreign_keys=ON), и сами файлы на диске. Внутри доски —
      долгое нажатие на фото без движения (в отличие от долгого нажатия +
      перетаскивания, которое двигает фото) открывает подтверждение
      удаления конкретного фото.

Все пункты из ТЗ реализованы хотя бы в базовом виде и компилируются как
общий каркас. Дальше — полировка, тестирование на реальных устройствах и
то, что обычно всплывает только при живой сборке (см. предупреждения по
версиям библиотек ниже).

## Разбор замечаний по производительности и стабильности

**1. Скролл фото шёл не плавно.** Реальная причина — Coil декодировал фото
в полном разрешении камеры (условно 4000×3000) под маленькую ячейку сетки
180×240dp. В `PhotoBoardGrid.kt` и `BoardsListScreen.kt` теперь передаётся
не голая строка, а `ImageRequest` с `.size(Size(720, 720))` (для доски) /
`.size(Size(480, 480))` (для превью на карточке доски) — Coil декодирует
сразу под нужный размер, а не в полный размер с последующим сжатием.
Кэш (память + диск) в Coil3 включён по умолчанию, отдельно настраивать не
нужно — просто в `ImageRequest` не создавался с явными `memoryCacheKey`/
`diskCacheKey`, что тоже поправлено.

**2. Фото "перебегает" мимо места при перетаскивании.** Здесь диагноз
"неправильный расчёт координат" был не совсем точен — расчёт целевого
индекса был верным, проблема в **асинхронности layout**. Компенсация
смещения (чтобы карточка не прыгала при перестановке в списке) считалась
сразу после мутации `order`, но `LazyVerticalStaggeredGrid` перекладывает
элементы не синхронно, а на следующий кадр — так что `bounds[photo.id]` в
этот момент были ещё старые. Итог: компенсация не срабатывала вовремя, а
когда реальная позиция наконец обновлялась, карточка визуально
"довыстреливала" мимо пальца. Исправлено переносом компенсации в
`onGloballyPositioned` — она теперь применяется именно в момент, когда
Compose реально сообщает новую позицию, а не по предположению.

**3. Дёрганный интерфейс.** Три источника: (а) индекс фото для клика
считался через `order.indexOfFirst {}` внутри тела каждого элемента на
каждой рекомпозиции — O(n) на элемент, O(n²) на всю сетку при большом
количестве фото; заменено на `itemsIndexed`, индекс приходит готовым.
(б) У некоторых, не участвующих в драге, карточек не было анимации
смены позиции — при реордере они мгновенно "телепортировались" на новое
место вместо того, чтобы плавно доехать; добавлен `Modifier.animateItem()`
для всех карточек, кроме самой перетаскиваемой. (в) Плюс общий эффект от
пункта 1 — decode тяжёлых bitmap на каждый скролл тоже вносил вклад в
ощущение "дёрганности", не только в скролл конкретно.

**4. Вылет при нажатии "Назад" внутри доски.** Не совсем вылет
(необработанное исключение), а отсутствие обработки вообще: в приложении
не было НИКАКОЙ связи между внутренней навигацией (список досок / доска /
просмотрщик — просто `mutableState` в `AppRoot`) и системной кнопкой
"Назад". Нажатие "Назад" внутри доски поэтому вело себя как обычное
закрытие Activity — то есть само приложение сворачивалось/завершалось
сразу, а не возвращало к списку досок, что и выглядело как "вылет".
Исправлено через `PlatformBackHandler` (`expect`/`actual`, на Android —
`androidx.activity.compose.BackHandler`, на Desktop no-op — там нет
системной кнопки "Назад"): теперь "Назад" сначала закрывает просмотрщик,
если он открыт, иначе возвращает от доски к списку досок, и только если
уже на списке досок — ведёт себя как обычно.

## Как собрать
1. Откройте папку `Interes/` в Android Studio (Koala+ с поддержкой KMP-плагина).
2. Дождитесь Gradle sync — он подтянет зависимости SQLDelight/Compose Multiplatform.
3. Для Android: выберите конфигурацию `androidApp`, обычная сборка/запуск на
   устройстве или эмуляторе (minSdk 26).
4. Для Windows: запустите Gradle-таск `desktopApp:run` для локального запуска,
   либо `desktopApp:packageMsi` / `packageExe`, чтобы получить установщик
   (jpackage должен быть доступен — идёт в комплекте с JDK 17+).

Версии плагинов в `build.gradle.kts` актуальны на момент написания скелета;
при первой синхронизации сверьте их с последними релизами Kotlin, Compose
Multiplatform, AGP и SQLDelight.

## Исправление ошибки версии плагина / AGP 9

Если вы создавали проект через мастер Android Studio ("New Project") и уже
после этого распаковывали сюда файлы Interes, у вас, скорее всего, осталась
папка `app` (со своим `build.gradle.kts`, `com.example.myapplication`) —
это не часть Interes, это мастер Android Studio. Она конфликтует с нашим
`androidApp` и является причиной ошибки `Error resolving plugin [id:
'com.android.application', version: '9.3.1'] ... already on the classpath
with a different version`.

Что сделать по порядку:
1. **Удалите папку `app`** целиком (проводник/файловый менеджер, не Android
   Studio — так надёжнее).
2. Откройте `settings.gradle.kts` в корне и, если там есть строка
   `include(":app")`, удалите её. В версии из этого архива её нет.
3. Замените в своём проекте следующие файлы содержимым из этого архива:
   `gradle/libs.versions.toml`, корневой `build.gradle.kts`,
   `shared/build.gradle.kts`, `androidApp/build.gradle.kts`,
   `desktopApp/build.gradle.kts`.
4. **Важно:** если у вас уже был свой `gradle/libs.versions.toml` от мастера
   Android Studio с другими номерами версий `agp`/`kotlin` — используйте
   именно ваши цифры (они уже скачаны и точно совместимы с вашей версией
   Android Studio), а не те, что в этом архиве. Просто допишите в свой файл
   недостающие ключи (`android-kotlin-multiplatform-library`,
   `compose-multiplatform`, `compose-compiler`, `sqldelight` и т.д.) по
   образцу.
5. File → Sync Project with Gradle Files.

### Почему поменялся сам `shared`-модуль, а не только версии

Начиная с AGP 9.0 (январь 2026) связка `id("com.android.library") +
kotlin("multiplatform")` в одном модуле официально не поддерживается —
Google выпустил отдельный плагин `com.android.kotlin.multiplatform.library`
специально под KMP. Раз у вас уже установлена версия Android Studio с AGP
9.3.1, тянуть со старым подходом не имело смысла — `shared/build.gradle.kts`
переписан на новый плагин: конфигурация Android-таргета переехала внутрь
`kotlin { android { ... } }`, отдельного `android { }`-блока верхнего уровня
в модуле больше нет. Подробности: https://developer.android.com/kotlin/multiplatform/plugin

### Встроенный Kotlin в AGP 9 (для androidApp)

Начиная с AGP 9.0 Kotlin-поддержка встроена прямо в `com.android.application`
и `com.android.library` и включена по умолчанию — отдельно подключать
`org.jetbrains.kotlin.android` (`kotlin("android")`) в модулях с этими
плагинами больше нельзя, это конфликт двух источников Kotlin-тулинга.
В `androidApp/build.gradle.kts` этот плагин убран, а `jvmTarget` для Kotlin
задаётся не через `android.kotlinOptions { }` (эта DSL ушла вместе со старым
плагином), а через отдельный top-level блок:
```kotlin
kotlin {
    compilerOptions {
        jvmTarget.set(JvmTarget.JVM_17)
    }
}
```
`shared`-модуля это не касается (там `org.jetbrains.kotlin.android` никогда
не было — `kotlin("multiplatform")` + `com.android.kotlin.multiplatform.library`),
`desktopApp` тоже не затронут (`kotlin("jvm")` со встроенным Kotlin в AGP не
связан). Подробнее: https://developer.android.com/build/migrate-to-built-in-kotlin

## Аудит кода (упор на Windows-сборку)

Полный проход по всем файлам проекта на предмет несостыковок и багов —
результат ниже. Практический вывод: раньше в этом README были
предупреждения "код не прогонялся через компилятор, вот вероятные места
правок" — эта формулировка больше не отражает реальность, ниже конкретные
найденные и исправленные проблемы, а не догадки.

### Обновлённые версии
Все зависимости сверены с актуальными на сегодня стабильными релизами и
сведены в `gradle/libs.versions.toml` целиком (ничего не захардкожено
по модулям отдельными строками):
- Kotlin 2.3.21 → **2.4.10** (была устаревшей);
- Compose Multiplatform 1.11.1 — актуальна, JetBrains гарантирует
  совместимость последней CMP с последним Kotlin;
- Coil3 3.0.4 → **3.5.0** (была устаревшей);
- `androidx.activity:activity-compose` 1.9.2 → **1.13.0**, вынесена в общий
  каталог вместо двух отдельных захардкоженных строк в
  `shared/build.gradle.kts` и `androidApp/build.gradle.kts` — именно такое
  расхождение версий одного артефакта в двух местах и было причиной самой
  первой ошибки сборки в этом проекте;
- SQLDelight 2.2.1 подтверждён как актуальный, но тоже вынесен в каталог
  (было 4 захардкоженные строки с одной и той же версией по разным
  source set'ам — риск рассинхронизации при следующем обновлении).

### Найденные и исправленные баги
1. **Критично, только Windows:** в `DatabaseDriverFactory.desktop.kt`
   проверка `!dbFile.exists()` шла ПОСЛЕ создания `JdbcSqliteDriver` и
   вызова `driver.execute(...)`. Открытие JDBC-соединения к `jdbc:sqlite:`
   само создаёт физический файл на диске — то есть на первом же запуске
   проверка видела файл как "уже существующий", `Schema.create()` не
   вызывался, и приложение падало на первом запросе к БД с
   `no such table: Board`. Исправлено: флаг "это свежая БД" фиксируется
   ДО создания драйвера.
2. **Только Windows:** диалог выбора файлов разрешал `.webp`, но
   `javax.imageio.ImageIO` (используется для определения размеров фото при
   импорте) не умеет декодировать WebP без сторонней библиотеки — импорт
   такого файла падал с "файл не распознан как изображение". `.webp` убран
   из фильтра; на Android эта проблема не касается — там `BitmapFactory`
   декодирует WebP нативно.
3. Копии фото на диске всегда получали расширение `.jpg`, даже если
   исходник был PNG (Android/Desktop) или WebP (Android) — не ломало показ
   (декодеры смотрят на содержимое, не на расширение), но было
   технически неверно. Исправлено на обеих платформах: Desktop берёт
   расширение исходного файла, Android — определяет его по реальному
   MIME-типу через `ContentResolver`.
4. **Логическая ошибка в нумерации фото:** `addPhotoToBoard` вычислял
   позицию нового фото как количество строк в доске (`count`), а не как
   реальный максимум `orderIndex + 1`. После удаления фото из середины
   списка (`[0,1,2,3]` → удалили индекс 2 → осталось `[0,1,3]`, но `count()`
   всё ещё 3) следующее добавленное фото получало уже занятый индекс —
   ломало сортировку и превью на карточке доски. Добавлен честный SQL-запрос
   `selectMaxOrderIndex`.
5. **Хрупкость drag-n-drop до уровня БД:** `PhotoBoardGrid.onReorder`
   передавал `fromIndex`/`toIndex` — позиции в списке `photos`, который
   репозиторий читает заново уже ВНУТРИ запущенной корутины. Если список
   успевал измениться между окончанием жеста и выполнением корутины
   (например, параллельно доехал импорт другого фото), индексы указывали
   бы не туда. Переделано на передачу готового списка id в новом порядке —
   `BoardRepository.reorderPhotos` применяет его напрямую по id, без
   зависимости от индексов.
6. `androidApp/build.gradle.kts` тянул захардкоженные
   `androidx.compose.material3:1.3.0` и `foundation:1.7.2`, хотя
   `MainActivity.kt` вообще не использует Compose API напрямую — весь UI
   приходит из `:shared` через Compose Multiplatform 1.11.1. Мёртвые
   зависимости с ДРУГИМИ версиями тех же артефактов создавали риск
   конфликта на класспасе. Убраны вместе с неиспользуемыми `core-ktx` и
   `lifecycle-viewmodel-compose`.
7. Запись `selectedBoardId = null` (когда открытую доску удалили) шла
   прямо в теле composable-функции вместо `LaunchedEffect` — анти-паттерн
   "запись состояния во время композиции" в Compose. Исправлено.
8. Сетки (`BoardsListScreen`, `PhotoBoardGrid`) были жёстко зафиксированы
   на 2 колонки (`GridCells.Fixed(2)` / `StaggeredGridCells.Fixed(2)`) — на
   телефоне нормально, но на широком окне Windows выглядело расточительно.
   Заменено на `Adaptive(minSize = 160.dp)` — колонок становится больше на
   широком окне, на узком (Android) эффективно остаётся 2.
9. Мелкая уборка: файл `PhotoViewerScreen.kt` переименован в
   `PhotoViewerContent.kt` (функция внутри была переименована раньше, файл —
   забыт), устаревшие комментарии в `AndroidManifest.xml` и коде обновлены,
   неиспользуемый плагин `kotlin-android` убран из каталога.

### Специфично для Windows-сборки — стоит проверить на реальной машине
- **Изменение размера окна.** Главное окно теперь `undecorated = true`
  (плата за реальную прозрачность до рабочего стола, см. `AppRoot.kt`) —
  `resizable = true` выставлен явно, но поведение "потянуть за край" у
  окна без рамки в Compose Desktop не всегда работает так же надёжно, как
  у обычного окна. Если не тянется — понадобятся свои resize-хендлы по
  краям, дайте знать.
- **Альфа-канал undecorated-окна** зависит от связки JDK/GPU-драйвера —
  разные машины могут повести себя чуть по-разному.
- Собирать/запускать `desktopApp` из Android Studio: полноценного
  "зелёного треугольника" у `fun main()` может не быть (Android Studio не
  всегда показывает gutter-иконки запуска для чистых JVM-модулей так же,
  как обычная IntelliJ IDEA) — надёжнее через панель Gradle:
  `Interes → desktopApp → Tasks → compose desktop → run`, либо
  `./gradlew :desktopApp:run` в терминале. Для установщика — тот же путь,
  но `packageMsi`/`packageExe`.
